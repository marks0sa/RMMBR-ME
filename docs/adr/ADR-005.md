# ADR-005: Use simple pattern for contact search
**Status:** Accepted
**Date:** 2026-11-24

## Context
Users need to find a contact later by remembering any detail about them: name, something from the description or notes, or the play they met. A typical user will have tens to a few hundred contacts. and every search is limited to that user's own contacts. I need to decide how search is implemented in the MVP, balancing usefulness against work of building and maintaining it.

## Options considered

**Simple pattern matching** 
Case-insensitive substring matching with the database's built-in operators across teh name, description, notes, and place fields. No extra setup and results are predictable: if text contains teh search term, the contact matches.

**PostgreSQL full-text search** 
Text is converted to indexed search vectors, which supports word stemming (search for "run" matches "running"), stop words, and ranking by relevance. It needs index configuration and a way to keep vectors up to date, and results are harder to predict.

**Trigram matching (pg_trgm extension)** 
Supports typo-tolerant, fuzzy matching and speeds up substring searches with an index. It needs an extension and an index, and similarity thresholds need tuning.

**Dedicated search engine (for example Elasticsearch):**
The most capable option, but a separate service to deploy, secure, and keep in sync with the database. This is far more than this project needs.


## Decision
Use simple case-insensitive substring matching in the MVP, always scoped to the logged-in user's contacts. Keep the search logic behind a single service method so implementation can be replaced without changing the API.


## Consequences

**Easier**
- No extra configuration, extensions, or indexes to maintain. 
- Behavior is easy to explain and to test: a term either appears in the text or it doesn't. 
- Searching only one user's rows keep the amount of data scanned small, so speed should be fine at this scale without a special index.

**Harder**
- No relevance ranking. Results are ordered by a chosen sort, not by how well they match.
- No stemming or synonyms, a search for "run" won't find "running" unless substring happens to match.
- No typo tolerance. A misspelled search finds nothing.
- Substring searches with a leading wildcard can't use a standard index, so each search scans the user's contacts.Acceptable for now, but would slow down if a single user had very many contacts.
- Searching across several fields can return noisy results for short terms.
