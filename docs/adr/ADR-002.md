# ADR-002: Use server-side session cookies for authentication

**Status:** Accepted
**Date:** 2026-11-23

## Context
RMMBR-ME stores personal information about people the user has met, so only the owning user may read or change a contact. The app is a browser-based React frontend talking to a Spring Boot API. Users need to log in, stay logged in, and log out. I need to choose how the API recognizes an authenticated user. 

## Options considered

**Server-side sessions with a cookie:** 
After login, the server creates a session, stores it, and sends the browser a session ID in a cookie. Each request carries the cookie and the server looks up the session. Spring Security supports this by default.

**JWT (token-based):** After login, servere issues a signed token that the client sends with each request. The server stores no session state, but tokens are hard to revoke before they expire. Storing one in browser JavaScript risks exploitation by bad actors and possibly would require cookies regardless.

## Decision

Use server-side sessions with hardened cookies and Spring CSRF protection.


## Consequences


**Easier**
- Logut and forced logout work immediately, because the server deletes the session.
- HTTPOnly keeps the session ID out of reach of JavaScript, which limits the damage of an XSS bug.
- It is the default Spring Security approach, so there is less custom security code to write and potentially get wrong.

**Harder**
- Cookies are sent automatically by browser, so API needs CSRF protection, and frontend has to send CSRF token with state-cahnging requests.
- frontend and API must be same-site. Across unrelated domains browsers may block cookie. Cross-Origin Resource Sharing must also be configured to allow credentials from the frontend's origin only.
- Sessions are server state. Default store is in memory, so users are logged out when the app restarts. 

Native mobile clients would favor tokens, but this project is a web app only.
