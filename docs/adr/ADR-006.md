# ADR-006: Model places as separate records that contacts reference

**Status:** Accepted
**Date:** 2026-11-24

## Context
The place where I met someone works as a category: ten people from the gym and three people from the coffee shop. Filtering the contact list by place is an MVP feature. Later (v1.2), the app will capture current location and suggest a real venue name, which means a place will eventually carry coordinates and a venue name as well as a label. I need to decide how a place is stored so the MVP filter works well and v1.2 doesn't require reworking data.

## Options considered

**Free text on each contact:** 
A "place" text column on the contact. Simplest to build, but "Gym", "gym", and "the gym" become three different filters, and renaming a place means editing every contact.

**Separate place record, referenced by contacts** 
A place table with a name, owned by one user. Each contact optionally points to one place. The user creates "Gym" once and selects it when adding people. Filtering is by place ID, so there are no spelling variants, and renaming a place updates every contact linked to it.

**Tags (many-to-many)**
A contact can have any number of tags, with places as one kind of tag. More flexible, but it also makes "where I met them" les explicit, and it adds a join table and more UI for a case where most contacts have one place.

## Decision

Create a place table owned by the user, and give each contact an optional reference to at most one place. Place names are unique per user, case-insensitive. Place records can later gain coordinates and venue details without changing contacts.


## Consequences


**Easier**
- Filtering by place is a simple, exact match with no duplicate variants.
- Renaming or correcting a place happens in one row.
- v11.2 has an obvious home for coordinates and venue names.
- Place filters can show counts ("Gym(10)") cheaply.

**Harder**
- More to build in the MVP: a place table, endpoints to manage places, and UI to pick or create one while adding a contact.
- Deleting a place needs a defined behavior: block the delete while contacts use it, or clear the place on those contacts. I'll decide one while implementing and note it.
- Every place query must be scoped to the owning user, as with contacts, so users can't see each other's places.
- One place per contact doesn't cover someone I meet in several settings. If that becomes common, tags or a many-to-many link would supersede this decision.
